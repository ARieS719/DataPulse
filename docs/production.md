# 生产化设计（S4 支线）—— 单机演示与生产平台之间的差距

> 本文档用于回答"这套平台生产化还差什么"：给出可对照的差距清单，而非泛泛而谈。
> 边界说明：本仓库是单机演示级实现，以下内容如实记录与生产平台的差距及演进路径。

## 1. 组件映射（本地 → 生产）

| 本地组件 | 生产候选 | 迁移要点 |
| --- | --- | --- |
| PySpark local[2] | 阿里云 EMR / AWS EMR / Databricks | 配置下推、动态资源分配、Spot 实例 |
| Airflow（单机 LocalExecutor） | DataWorks / Astronomer / MWAA | DAG 权限、SLA 告警、回填策略 |
| 自研质检引擎 | 自研平台化 / DataWorks DQC | 规则市场、审批流、多租户隔离 |
| Redis 水位线 | Tair / ElastiCache | 持久化、集群分片 |
| PostgreSQL | RDS / PolarDB | 高可用、审计日志、备份策略 |
| ChromaDB 本地 | 向量库集群 / 托管服务 | 知识库分区、权限、版本管理 |
| 单机元数据 | DataHub / OpenMetadata | 与平台元数据中心双向同步 |

## 2. 生产架构（多租户平台化）

```
                  ┌────────────────────────────────────────────┐
                  │  质量平台控制面：规则市场 · 审批流 · 告警分级  │
                  └──────────────┬─────────────────────────────┘
                                 │ 规则集 / 水位线 / 血缘 / 审计
   ┌─────────────┬───────────────┼────────────────┬─────────────┐
   ▼             ▼               ▼                ▼             ▼
规则市场    告警中心         血缘服务         质检执行集群      审计与合规
(模板/版本) (P0电话/P1群)  (DataHub同步)    (EMR on-demand)  (全链路留痕)
```

生产化新增能力（本仓库刻意不做）：
1. **多租户**：规则集/水位线按租户隔离，权限 RBAC；
2. **规则审批流**：AI Copilot 生成 → 人工审批 → 灰度生效 → 全量；
3. **告警分级通道**：P0 电话/值班群 + 熔断；P1 群消息；P2 日报聚合；
4. **质检执行集群**：扫描任务按表规模弹性伸缩（10 亿行场景）；
5. **审计合规**：规则变更、熔断决策、数据合并全程留痕可追溯。

## 3. 规模演进（100 万行 → 10 亿行）

| 问题 | 本地已验证 | 生产方案 |
| --- | --- | --- |
| 扫描耗时 | 单次合并扫描（规则数不增加扫描次数） | 分区裁剪 + 增量分区扫描（只扫当日分区） |
| 数据倾斜 | 第 9 类混沌故障（data_skew）单测 | AQE + 两阶段聚合 + 加盐 |
| 小文件 | rewrite_data_files 接口 | 定时 compaction 任务 + 写入侧合并 |
| 水位线容量 | Redis 30 天日粒度 | 小时粒度 + 降采样保留 90 天 |
| 血缘图规模 | 30 脚本 <500ms | 增量解析 + 版本化存储，图谱服务化 |

## 4. 成本模型（估算口径）

单次质检成本 ≈ 扫描数据量 × 单价 + 引擎固定开销：
- 增量分区扫描（日分区 1/30 数据量）使单次成本降至全量扫描的 ~1/30；
- 规则合并扫描相对逐规则扫描（GE 模式）节省 ≈ (规则数 - 1) 次全表扫描；
- 这是"为什么自研 + 为什么 WAP"的成本侧论据，可直接用于量化评估。

## 5. 差距清单

1. 真实生产规模与多租户平台化（本仓库：单机 100 万行）；
2. 实时链路的质检（设计：Flink SQL 分钟级窗口 + 同一套规则元数据，见 S5）；
3. 与公司元数据中心（DataHub/OpenMetadata）的双向同步；
4. 质量运营体系的长期数据积累（规则覆盖率/拦截率/误报率趋势）；
5. 安全合规（数据分级、脱敏策略的下沉与审计）。
